# Coding standards and practices for THIS application

## Important Note:
These standards should take precedence over EVERYTHING else in the Boost Guidelines information.
If any rules in this section conflict with any rules in any other section, the rules within THIS section should be prioritized.

### 1. Naming Conventions

```
✅ CORRECT:
- Models: Video (singular, StudlyCase)
- Tables: videos (plural, snake_case)
- Pivot Tables: post_tag (singular snake_case, alphabetical order)
- Foreign Keys: user_id (singular_table_name_id)
- Singular Relationships (i.e., belongsTo, hasOne, etc.): post(), colorScheme, relatedModel() singular camelCase of the related model name
- Multiple Relationships (hasMany, belongsToMany, etc.): posts(), colorSchemes, relatedModels() plural camelCase of the related model name

❌ WRONG:
- Model: Videos (can not be plural - must be singular)
- Table: Video (can not be singular, Studly - must be plural snake_case)
- Foreign Key: userId (can not be camelCase, must be snake_case as {singular_table_name}_id)
- Pivot: tag_post (must be in alphabetical order)
- Pivot: posts_tags (each table part must be singular)
- Relationship: tagPost() (NO! if no TagPost model exists - do not combine model names, reference ONLY the model name that the relationship is pointing to)
```

### 2. Database Rules

```
✅ Primary Keys: Always 'id' (auto-increment integer)
✅ Foreign Keys: Always '{singular_table_name}_id' format
✅ Pivot Tables:
   - NO 'id' column
   - Composite primary key from foreign keys
   - Composite unique key (automatically added)
   - NO timestamps
   - Alphabetical naming: post_tag not tag_post
   - Both foreign tables MUST exist first
✅ Timestamps: created_at and updated_at on all non-pivot tables set to NOW()
✅ Must have at least one unique column (outside of id)
✅ NEVER use ENUMs as column type
✅ Make every attempt to avoid JSON as column type
✅ Composite unique keys with 2 args should be set as {table_name}_composite_unique
✅ Composite unique keys with 3+ args should be set as {table_name}_multi_composite_unique
✅ If more than one 2 arg composite unique, append alphabet (i.e., {table_name}_composite_unique_a, {table_name}_composite_unique_b, etc.)
✅ If more than one 3+ arg composite unique, append alphabet (i.e., {table_name}_multi_composite_unique_a, {table_name}_multi_composite_unique_b, etc.)
```

### 3. Testing
EVERY model and standalone function MUST have a corresponding PEST test. 

### 4. General
- Codebase MUST be DRY. DO NOT REPEAT functionality logic ANYWHERE in the application. If a new class/method/function 
uses logic that is already in use somewhere, immediately ABSTRACT the logic in use to a location that can be accessed 
by both code blocks, and implement the abstracted logic in both sections (and everywhere else it may be needed going 
forward). As mentioned in number 3, this abstracted logic MUST have a corresponding PEST test.

  - When to DRY abstract: Whenever/wherever there is a section of code that contains at least one logic check, and is used 
  in more than one place.
- NEVER hardcode data as an argument or otherwise. Either retrieve data from the database or set it in a config. NEVER hardcode it in the logic.
- Employ SOLID principles in all code logic/structure/etc.
  - Single Responsibility Principle
    A class should have only one reason to change.
    It should have a single, well-defined responsibility. 
  - Open/Closed Principle
    Software entities (classes, modules, functions, etc.) should be open for extension but closed for modification.
    This means you should be able to add new functionality without changing existing code. 
  - Liskov Substitution Principle
    Objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program.
    Subtypes must be substitutable for their base types. 
  - Interface Segregation Principle
    Clients should not be forced to depend on interfaces they do not use.
    It is better to have many small, specific interfaces than one large, general-purpose one. 
  - Dependency Inversion Principle
    High-level modules should not depend on low-level modules. Both should depend on abstractions.
    Abstractions should not depend on details. Details should depend on abstractions.
- All models should follow the Repository Pattern, and should have a corresponding Factory, Interface, Repository (at least one MySQL, Postgres or Eloquent), Form Request, Controller, Service and Test.
  - NOTE: These can all be auto-generated by the make:api-bundle artisan command
